# Drizzle — the persistence ring

Drizzle is a **typed query builder, not an ORM with a mapper**. It will not give
you domain objects; it gives you row shapes inferred from the schema. Nothing
stops those shapes spreading through the application unless you stop them.

That is the whole discipline on this ring:

> `drizzle-orm` and the DB schema are imported by repositories (and the schema /
> DB client files) and by nothing else in the feature modules.

Checked by `orm_import_leak`, `query_outside_persistence` and `row_types_leak`
in `check-onion.sh`; an import-graph gate can enforce it too (`no-routes-to-db`,
`no-service-to-db`, `no-module-helpers-to-db`). Query mechanics are in
`engineering-paved-path:drizzle-orm-patterns`; schema design in
`engineering-paved-path:postgresql-table-design`.

## The repository

```ts
export class ProjectRepository {
  constructor(private db: Db) {}

  async list(tenantId: string): Promise<ProjectRow[]> {
    return this.db.select().from(t.projects).where(eq(t.projects.tenantId, tenantId));
  }
}
```

Three invariants:

1. **It takes the DB handle, not the container.** The service holds the
   container and passes the handle down: `this.repo = new ProjectRepository(container.db)`.
2. **Every query is scoped by the tenant / owner id** when the schema is
   multi-tenant. An unscoped query is a tenancy bug the moment real auth arrives.
3. **It owns one table** (or one tightly-bound cluster). When a module's
   repository gets crowded, split it into `repository/<entity>.repo.ts` files —
   that is the right move, not a bigger file.

## Row types stop here

```ts
// ✅ repository returns a row; a mapper turns it into the contract DTO
export function toProjectDto(row: typeof t.projects.$inferSelect): Project { … }

// ❌ a row type as an application-layer parameter
async function runOneJob(project: typeof schema.projects.$inferSelect, …)
```

The cost of the second form: a column rename in a migration silently retypes a
function three rings out, and the application layer now depends on naming
decisions that belong to the schema.

The mapper often performs a field-name flip (Drizzle fields `camelCase`, contract
JSON `snake_case`, or the reverse). That translation is exactly why the mapper
exists, and exactly what a leaked row skips. Keep the mapper beside the
repository (or in a `*.mapper.ts` / `mappers/` file — the check's default
persistence pattern allows both).

A shared row-types file (e.g. `src/db/rows.ts`) is the sanctioned place to
*name* a row type, so a cross-cutting consumer does not import another module's
repository. Naming it there does not make it safe to pass around on ring 5 or 6.

## Transactions

- the **service** decides the boundary — it knows which steps must be atomic;
- the **repository** executes it — the callback and the `tx` handle never escape
  the persistence ring;
- pass `tx` into repository methods rather than letting a service hold a Drizzle
  handle.

```ts
// service.ts — boundary, no query
await this.repo.withTransaction(async (tx) => {
  await this.repo.insertOrder(tx, order);
  await this.repo.insertLines(tx, lines);
});
```

## Migrations

The schema files are the source of truth; migration SQL is generated by
`drizzle-kit` and never hand-edited. A schema change is generate → migrate, using
the project's scripts. Prefer running migrations as an explicit step rather than
on boot. Check the project's convention before changing either.

Tables with no rows yet are not dead code; do not "clean them up" while adding a
repository.
